# .env.example — Environment Variables Guide

## 1. Introduction

Environment variables are used to store configuration values outside the main application source code.

In a Next.js project, they can configure API endpoints, database connections, authentication providers, and other services.

The `.env.example` file provides a template showing which environment variables a developer may need to configure.

Official Documentation: https://nextjs.org/docs/app/guides/environment-variables

## 2. What Is an Environment Variable?

An environment variable is a named value that an application reads from its execution environment.

Example:

```bash
API_BASE_URL=https://api.example.com
```

The application can access this value on the server using:

```typescript
process.env.API_BASE_URL
```

Environment variables help separate application configuration from source code.

## 3. What Is .env.example?

The `.env.example` file documents the environment variables required or optionally supported by a project.

It should contain placeholder values rather than real credentials.

Example:

```bash
# Application
NEXT_PUBLIC_APP_NAME=My Next.js App
NEXT_PUBLIC_APP_URL=http://localhost:3000

# Backend API
API_BASE_URL=http://localhost:8000

# Database
DATABASE_URL=

# Authentication
AUTH_SECRET=

# Optional external service
EXTERNAL_API_KEY=
```

These names are examples. Keep only variables that the actual project uses, and follow the requirements of the selected libraries.

## 4. Common Environment Variables

### NEXT_PUBLIC_APP_NAME

A public application name that may be displayed in the browser.

Example:

```bash
NEXT_PUBLIC_APP_NAME=My Next.js App
```

### NEXT_PUBLIC_APP_URL

The public base URL of the application.

Example:

```bash
NEXT_PUBLIC_APP_URL=http://localhost:3000
```

Replace the value with the appropriate URL for each environment.

### API_BASE_URL

The base URL of a backend API.

Example:

```bash
API_BASE_URL=http://localhost:8000
```

Keep this variable server-side if it does not need to be exposed to the browser.

### DATABASE_URL

A database connection string.

Example placeholder:

```bash
DATABASE_URL=
```

The format depends on the database provider and database driver used by the project.

Never commit a real database connection string or password.

### AUTH_SECRET

A secret used by an authentication library when required.

Example placeholder:

```bash
AUTH_SECRET=
```

Generate a strong, unique secret using the authentication library's recommended procedure.

Do not use a sample secret in production.

### EXTERNAL_API_KEY

An API key for a third-party service.

Example placeholder:

```bash
EXTERNAL_API_KEY=
```

Use the exact variable name expected by the corresponding SDK or application code.

## 5. Public and Private Variables

### Public variables

Next.js exposes environment variables prefixed with `NEXT_PUBLIC_` to browser-side code when they are referenced in supported ways.

Example:

```bash
NEXT_PUBLIC_APP_NAME=My Next.js App
```

Only put values here that are safe for users to see.

### Private variables

Variables without the `NEXT_PUBLIC_` prefix are not automatically exposed to browser code, but they must still be used carefully.

Example:

```bash
DATABASE_URL=
AUTH_SECRET=
EXTERNAL_API_KEY=
```

Read private variables only in appropriate server-side code.

Important: Never place passwords, private API keys, authentication secrets, or database credentials in `NEXT_PUBLIC_` variables.

## 6. Where to Store Environment Variables

A typical Next.js project may use these files:

- `.env.example` — documents expected variables using placeholders.
- `.env.local` — local development configuration.
- `.env.development` — development environment configuration.
- `.env.production` — production configuration when managed locally or by the deployment environment.

Next.js loads environment variables according to its documented loading rules.

Keep actual secrets out of GitHub. Make sure `.env.local` and other files containing secrets are excluded by `.gitignore`.

## 7. How to Set Up Environment Variables

### Step 1: Create a local environment file

From the project root, copy `.env.example` to `.env.local` if the example file exists.

On Windows Command Prompt:

```cmd
copy .env.example .env.local
```

On macOS or Linux:

```bash
cp .env.example .env.local
```

### Step 2: Add real development values

Edit `.env.local` and fill in the values required by your application.

Do not replace placeholders with production credentials in a file intended for GitHub.

### Step 3: Restart the development server

After changing environment variables, restart the Next.js development server when necessary.

```bash
npm run dev
```

### Step 4: Verify the configuration

Confirm that required variables exist and that the application handles missing values appropriately.

Avoid printing secrets to terminal logs or exposing them in browser responses.

## 8. Example .gitignore Rules

Use `.gitignore` to prevent local secret files from being committed.

Example:

```gitignore
.env*
!.env.example
!.env.example.md
```

This is an illustrative pattern. Review the existing `.gitignore` carefully before changing it, and confirm that files containing real secrets remain excluded.

## 9. Environment Variable Validation

Validate required environment variables when the application starts or when the relevant server-side functionality runs.

Example:

```typescript
const apiBaseUrl = process.env.API_BASE_URL

if (!apiBaseUrl) {
  throw new Error('API_BASE_URL is not configured')
}
```

For larger applications, use a dedicated validation schema if appropriate.

Do not expose private environment variables through API responses or client components.

## 10. Supabase Configuration (Optional)

If the project uses Supabase, the following variables are common:

```bash
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_ANON_KEY=
SUPABASE_SERVICE_ROLE_KEY=
```

Use the exact variable names expected by your installed Supabase client and application code.

Security rules:

- The project URL is generally public configuration.
- A publishable or legacy anon key is intended for client-side use only under the provider's security model and with appropriate Row Level Security policies.
- Never expose a Supabase service role key to the browser.
- Keep privileged credentials server-side.
- Verify the current Supabase key format and official guidance before deployment.

Official Documentation: https://supabase.com/docs

## 11. Common Mistakes

### Missing environment variable

Check whether the variable is defined in the correct local or deployment environment.

### Incorrect variable name

Environment variable names are case-sensitive in many environments. Match the name used by the application code.

### Secret exposed to the browser

Remove the `NEXT_PUBLIC_` prefix from private variables where appropriate, move their usage to server-side code, and rotate any credentials that have already been exposed.

### Changes are not applied

Restart the development server and check the environment loading rules.

### Environment file committed accidentally

Remove the secret from the repository and its history where necessary, rotate the exposed credentials, and review repository access. Deleting the file alone does not invalidate a leaked secret.

## 12. Best Practices

1. Maintain a documented list of required variables.
2. Use placeholder values in `.env.example`.
3. Never commit real credentials.
4. Use `NEXT_PUBLIC_` only for browser-safe values.
5. Validate required server-side configuration.
6. Keep development, testing, and production credentials separate.
7. Store production secrets in your hosting provider's secret-management settings.
8. Document optional variables and their purposes.
9. Keep `.gitignore` rules consistent with your project.
10. Review official provider documentation before configuring authentication or database access.

The `.env.example` file helps developers understand which environment variables a project needs without sharing private credentials.

Use it as a safe configuration template, maintain a separate local environment file, and protect all secrets during development and deployment.
